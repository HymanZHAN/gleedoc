# gleedoc

[![Package Version](https://img.shields.io/hexpm/v/gleedoc)](https://hex.pm/packages/gleedoc)
[![Hex Docs](https://img.shields.io/badge/hex-docs-ffaff3)](https://hexdocs.pm/gleedoc/)

A **doc test** library for Gleam, inspired by Rust and Elixir's doctest tooling.

Doc tests let you write executable examples in your documentation comments (`///`).
These examples are extracted, compiled, and run as part of your test suite,
ensuring your documentation never goes out of date.

## How it works

1. **Extract** `///` doc comments from your `.gleam` source files.
2. **Find** fenced code blocks tagged with `gleam` inside those comments.
3. **Generate** test modules in your `test/` directory.
4. **Run** the generated tests with `gleam test`.

## Installation

```sh
gleam add gleedoc --dev
```

## Usage

Write doc comments with `gleam` code blocks in your source files:

````gleam
// src/math.gleam

/// Adds two numbers together.
///
/// ```gleam
/// let result = add(1, 2)
/// let assert True = result == 3
/// ```
pub fn add(a: Int, b: Int) -> Int {
  a + b
}
````

Then run gleedoc to generate tests:

```sh
gleam run -m gleedoc
```

This creates `test/gleedoc_generated_math_test.gleam` containing:

```gleam
// Generated by gleedoc - do not edit manually

import gleeunit/should
import math

// From: src/math.gleam:4
pub fn gleedoc_add_1_test() {
  let result = add(1, 2)
  let assert True = result == 3
}
```

Now run your tests as usual:

```sh
gleam test
```

## API

You can also use gleedoc programmatically from your test suite:

```gleam
// test/gleedoc_setup.gleam
import gleedoc

pub fn main() {
  let config = gleedoc.GleedocConfig(
    module_name: "my_module",
    package_name: "my_package",
    output_dir: "test",
    source_dir: "src",
  )

  case gleedoc.run(config) {
    Ok(Nil) -> Nil
    Error(snag) -> panic as snag.message
  }
}
```

## How other languages do it

| Language   | Approach                                                                      | Key Difference from Gleam                 |
| ---------- | ----------------------------------------------------------------------------- | ----------------------------------------- |
| **Rust**   | `cargo test` compiles ` ```rust ` blocks from `///` comments. No REPL needed. | Gleam follows this model closely.         |
| **Elixir** | `doctest Module` parses `iex>` prompts from `@doc` strings.                   | Elixir has a REPL; Gleam does not.        |
| **Python** | `doctest` parses `>>>` prompts from docstrings.                               | Python is interpreted; Gleam is compiled. |

Because Gleam is a compiled language with no built-in REPL, **gleedoc** adopts
Rust's approach: doc blocks are treated as standalone Gleam code that gets
compiled and executed. If a block panics, the test fails.

## Architecture

```
src/
  gleedoc.gleam           # Main entry point and CLI
  gleedoc/
    extract.gleam         # Line-based doc comment extraction
    parse.gleam           # Markdown code block parsing
    generate.gleam        # Test file generation
```

### Key dependencies

| Package      | Role                                                 |
| ------------ | ---------------------------------------------------- |
| `glance`     | Gleam source parser (used for structural validation) |
| `simplifile` | Cross-target file I/O                                |
| `snag`       | Lightweight error handling                           |

## Roadmap

### Implemented

- [x] Extract `///` doc comments from source files
- [x] Parse ` ```gleam ` fenced code blocks
- [x] Generate compatible `gleeunit` test files
- [x] Multi-file source discovery
- [x] Use `glance` to extract public names for unqualified imports
- [x] Single-command `gleam run -m gleedoc` CLI experience

### Missing Features (compared to Rust, Elixir, and Python)

| Feature | Rust | Elixir | Python | **gleedoc** |
|---------|------|--------|--------|-------------|
| `ignore` / skip attribute | ✅ | ✅ | ✅ | ❌ |
| `no_run` (compile only) | ✅ | ❌ | ❌ | ❌ |
| `should_panic` | ✅ | ❌ | ❌ | ❌ |
| Hidden setup lines (`#`) | ✅ | ❌ | ❌ | ❌ |
| Output assertions (`// ->`) | ❌ | ✅ (`iex>`) | ✅ (`>>>`) | ❌ |
| Module-level doc tests | ✅ (`//!`) | ✅ | ✅ | ❌ |
| `compile_fail` | ✅ | ❌ | ❌ | ❌ |
| Multi-target (`erlang` / `javascript`) | ✅ (`cfg`) | ❌ | ❌ | ❌ |
| Incremental / cached generation | ✅ | ✅ | ✅ | ❌ |
| Source-mapped error reporting | ✅ | ✅ | ✅ | ❌ |

#### High Priority

1. **Doc block attributes** — Parse modifiers on the fence tag:
   ```gleam
   /// ```gleam,no_run
   /// launch_rocket()  // compiles, never runs
   /// ```
   ///
   /// ```gleam
   /// // gleedoc: ignore
   /// broken_code()    // skipped entirely
   /// ```
   ```

2. **Output assertions** — Assert on printed output, similar to Elixir's `iex>`:
   ```gleam
   /// ```gleam
   /// io.println(greet("world"))
   /// // -> Hello, world!
   /// ```
   ```

3. **Hidden lines** — Lines prefixed with `#` are included in tests but hidden from rendered docs:
   ```gleam
   /// ```gleam
   /// # let setup = [1, 2, 3]
   /// let len = list.length(setup)
   /// let assert True = len == 3
   /// ```
   ```

4. **Module-level doc tests** — Support doc comments at the top of a file that aren't attached to a specific definition.

#### Medium Priority

5. **Precise definition mapping via `glance`** — Currently gleedoc uses line-based regex heuristics to associate `///` blocks with definitions. Using `glance` source positions would make this robust across attributes, generics, and multi-line signatures.

6. **Better error reporting** — Failures currently point to the generated test file. Ideally errors would report the original source file, line number, and doc comment text.

7. **Incremental / cached generation** — Only regenerate test files when the corresponding source file changes (e.g. hash-based cache in `build/gleedoc.cache`).

8. **Cross-module imports in doc tests** — Automatically detect `import` statements inside code blocks and include them in generated tests.

#### Low Priority

9. **Target-aware tests** — Run certain doc tests only on Erlang or JavaScript targets.
10. **`compile_fail`** — Verify that intentionally invalid code produces a compile error.
11. **Panic message matching** — Assert that a panic produces a specific message (`should_panic(expected = "...")`).
12. **Documentation coverage** — Report which public functions lack doc test examples.
